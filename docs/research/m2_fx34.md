# M2 research: screen effects (fades, effects, blur) for views 3-4

Build: The Warriors SLUS-21215 v1.03 (`local/disc/SLUS_212.15`, opened read-only). Date: 2026-10-11.
Method: static analysis only, nothing was run (no emulator). Sources: Ghidra decompile `local/analysis/all/*.c`,
`callers.pkl`, `lua_bindings.tsv`, ELF strings, and our own R5900 disassembly of the ELF (scratch tools, not in the
repo). Function and structure names are OUR labels (the ELF is stripped). Addresses are static (ELF).
Builds on `m2_pads_cameras.md` section 3 and Appendix B (the 4-entry ScreenEffects mirror at 0x000F0890) and does not
touch the three player-indexed users already fixed in `m2_inventory34.md` block A6 (FUN_00284280, FUN_00236D28,
FUN_00236FB8).

## 0. Result in plain English
- **The bug (user report).** In a 2x2 split, at GAME OVER the views of players 1-2 fade to black and the views of
  players 3-4 keep showing the game.
- **Cause (VERIFIED, static).** The GAME OVER screen starts its fade with a loop that only walks the first two
  ScreenEffects objects (one object per view). Views 3-4 have their own objects (the 4p group creates 4), but nobody
  tells them to fade. Many other effects have the same 2-view loop.
- **Which function is the game-over fade.** `FUN_001D23D0` (our label `GameOverScreen::Enter`): it calls the fade
  function `FUN_0018D450(2.0 s, object, mode 1 = fade to black)` for objects 0 and 1. The screen's exit,
  `FUN_001D1C48`, clears the fade again (mode 0, time 0). A second game-over screen, used only for mission ids
  0x3C-0x45, fades in its update function `FUN_001CF468`. Section 1 has the trace.
- **The fix.** Point each loop at the mirror 0x000F0890 and loop to 4. Where a loop does more than walk the effect
  objects, a small code cave is used instead. Appendix: **232 pnach words** (116 in-place words, 100 cave words at
  0x000E5800-0x000E59AB, 16 data words at 0x000E5C00-0x000E5C3F that are zeroed once at load).
- **The old list of 19 was incomplete.** It had the "start" half of several pairs but not the "end" half (EndRain,
  EndFog, EndRoomSmoke, ExitStore...), not the tint restore, and not three more loops. Extending only one half
  would leave rain or a tint stuck on views 3-4. 16 more functions are included (section 4).
- **Loop to 4 or to the live view count?** Loop to 4 is right for every function that changes the objects, because all
  4 objects exist from boot. The exception is the reader `FUN_003A6EE8`. It must use the live view count (with a floor
  of 2, as in the original), otherwise a fade left pending on a view that is not drawn would block it forever
  (section 5).
- **Check.** `note_patches.py check` with `mod/w4p_m1.pnach`, the inventory fragment and this fragment:
  **0 new problems**. The 6 problems it prints already exist in the pnach (section 8).
- Nothing here was run. Section 7 lists the runtime tests.

So once objects 2 and 3 get the same fade call, views 3-4 go black too. The draw side already covers 4 views.

**The fade function `FUN_0018D450(f12 time, a0 object, a1 mode, a2, a3)` (VERIFIED).** It uses a jump table at
0x00552F70. Mode 0 = fade in (sets 0x00510174 = 1). Mode 1 = fade to black. For mode 1 it first checks the player
whose handle is at GameMgr+0x228 + 4*view (object +0x212 = view index), so views 2-3 read handles 2-3. That is valid
in the 4p group, which grows the handle array to 4 and sets empty slots to -1. Modes 2/3 = `FUN_0018D868`, modes 4/5 =
`FUN_0018D058`. Both fade modes end in `FUN_0018CC60`.

**Other game-over and result screens (VERIFIED).**
- Screen A at 0x00623040 (vtable 0x0053B1B0, state id 0xD, mission ids 0x3C-0x45). Its enter `FUN_001CEF10` does not
  fade. Its update `FUN_001CF468` fades all views to black (2 s) when the continue counter 0x00619910 runs out. Its
  exit `FUN_001CF358` calls `FUN_001D1C48`.
- Screen D at 0x00635390 (vtable 0x0053BEE0, state id 0x14) is the Rumble win screen (Lua `HUDLaunchRumbleWin`). Its
  enter `FUN_001E0008` fades all views to black (2 s). Its exit `FUN_001E0430` calls `FUN_001D1C48`.
- Mission complete (Lua `HUDLaunchMissionComplete`, state 0xB) and the level and loading states fade through
  `FUN_0018B168` (Lua `ScreenQueueEffect`). It is called from `FUN_001596D0`, `FUN_0015D890`, `FUN_0015E238` and
  `FUN_0015ECA0` with 1.0 s or 1.5 s.

## 2. Method and checks
- An R5900 disassembler and encoder were written in the scratchpad. Every "was" word in the appendix was read from the
  ELF. Every new word was encoded and then disassembled back (the comment after `->` is that disassembly).
- **Shared `lui` check.** For each patched `lui`, the following instructions were scanned up to the point where the
  register is overwritten, and branches into that window were listed. In every case the `lui` feeds only the patched
  `addiu`, except one: in `FUN_001276A0` and `FUN_0013CCD8` the `addiu` is also reached from a branch whose delay slot
  holds a second `lui v0,0x60` (0x00127734, 0x0013CD3C). Both `lui`s are patched. On the not-taken path `v0` is
  overwritten by the next call, so this is safe.
- **After-loop check.** The counter and pointer registers are not read after any loop exits before they are
  rewritten. The scan is linear. Its one hit (0x001CF8DC) is on the other side of an unconditional branch.
- **Branch-target check.** No branch lands inside a replaced instruction sequence, except where it is intended:
  0x0012D1F4, 0x0013D5FC and 0x003A6F10 are reached by branches, and the new code there is valid on every path.
- **Caves.** They are at 0x000E5800-0x000E59AB, with data at 0x000E5C00-0x000E5C3F. Nothing in `mod/w4p_m1.pnach`
  writes there. The inventory fragment uses 0x000E4000-0x000E501B. A cave entered with `jal` only clobbers `ra` in
  functions that saved `ra` on their stack and reload it before returning (checked in each function).

**Tint slots.** States are kept on a stack: array 0x005E66A0, depth word 0x0050C784 (-1 when empty). The save
(`FUN_00155F78`) always runs on the top state. The only restore caller is `FUN_0015E650`, which lowers the depth
before calling `FUN_00155FF0`. So views 2-3 are saved in slot `depth & 7` and restored from slot `(depth + 1) & 7`
(8 slots x 2 words at 0x000E5C00). This keeps nested states (pause, then a submenu) correct.

The simpler idea, giving views 2-3 the saved tints of views 0-1, was rejected. Some tints are per player, for example
rage through `FUN_0018B7D0` on the player's own object. That idea would copy player 1's rage tint onto view 3.

## 5. Loop to 4 or to the live view count (answer to the HYPOTHESIS)
- **4 is safe for the writers** (HYPOTHESIS, strong). All 4 objects exist from the creation loop at boot
  (`FUN_0018BA10`, called from `FUN_00160DF8` before the boot movies). The level reset `FUN_0018C058` already resets
  4 objects. The draw loop `FUN_0018DAC0` only draws views below the live count. In a 1-2 player game, objects 2-3
  receive the same calls, are never drawn, and are reset at every level load. The call side effects outside the
  objects are idempotent flags: `FUN_00183618`/`FUN_00183628` set a rain flag to 1/0, `FUN_001B2658` resets HUD 0/1,
  and `DAT_00510174 = 1`. The mode-1 fade looks up player handles 2-3, which are -1 when empty (`m2_gamemgr.md`), so
  `FUN_00390268` returns 0 and that step is skipped.
- **Exceptions handled above.**
  - The shared loop in `FUN_001E0008` (guard cave).
  - The state save in `FUN_00155F78` (it would overwrite the vtable).
  - The render loop in `FUN_0042A938` (not repeated).
  - The reader `FUN_003A6EE8` (live view count).
- **Why the reader needs the live count.** A fade only advances while its view is drawn (`FUN_0018CE58`). With a fixed
  bound of 4, a fade started on an undrawn view stays "running" forever, and `FUN_003A6EE8` would never draw again in
  1-2 player games. The floor of 2 keeps the original 1-2 player behaviour exactly.
- **Cosmetic side effect (HYPOTHESIS).** When a player joins mid-level, their view may replay the last fade that was
  queued on its object (for example a 1 s fade-in from black). This lasts at most the fade time.
- **Heap (HYPOTHESIS).** Rain, Fog and RoomSmoke allocate 0x100/0x130/0x100 bytes per extra view, and only while the
  effect runs: at most 0x660 bytes for views 2-3 together.
