# M6 fixes X4 (teleport follow) and X6 (run Lua source in the game): implementation and single-instance tests (2026-10-12)

## Plain-English summary
- **X4 works.** When a mission script moves player 1 or player 2 somewhere else (a "teleport"), players 3 and 4 used
  to stay behind. Now, right after such a script teleport, every player 3/4 who is more than 15 units away from
  player 1 is put next to player 1 (the game's own "put him near that person" routine finds a free spot). Example: in
  Mission 13 the script's own teleport after the trainyard scene pulled players 3 and 4 from about 65 units away to
  3.6 and 6 units from player 1. With X4 switched off, the same kind of teleport left them about 100 units behind.
- **X6 is no longer blocked.** The game keeps its Lua "brain" (the lua_State) inside its script object, whose address
  is stored at 0x00512B04; the lua_State is the word at offset +4. A small routine (LUARUN) now runs any Lua text on
  the game thread. Tested: it sets and reads back global variables, sees the mission's own variables (`player`,
  `player2`), reports syntax errors without harming the game, and can call any script command (teleports, money).
- **Fixes now load automatically with each mission.** A second small hook (LUACH) sees every script file the game runs
  ("level9.lua", "level9_chap1_radio.lua", ...) and runs our own Lua text right after a named file. It is switched on
  in `mod/m2/missions.txt` with one row: the Mission 13 camera fix below.
- **A real bug was confirmed and fixed:** in Mission 13 the subway trigger `EnterGraveTrain`, when touched by player 3,
  permanently swapped **player 3's own view** to a subway camera (screenshot evidence). A one-line Lua guard stops it;
  players 1-2 still use the trigger as before.
- **Not done / open:** the other script fixes (Missions 3, 6, 11, 16, 18) are proposals only (section 3); the M13 guard
  was tested by calling the trigger function directly, not by walking player 3 into the trigger; views 3-4 show a dark
  frame for about a second after a follow teleport (their camera catches up). Everything is SINGLE-PC, one instance,
  scripted bots; no human play.

Build: The Warriors SLUS-21215 v1.03 (`local/disc/SLUS_212.15`, read-only), fork build w4p-m6-1 (not rebuilt;
`emulator/` untouched). Function and structure names are OUR labels (the ELF is stripped); addresses static unless
marked dynamic. Labels: VERIFIED (with pointer), HYPOTHESIS, BLOCKED, FAILED TEST. **All tests: SINGLE-PC, one
instance (sandbox 12), scripted bot input, no impairment, MTVU off**, Mission 13 (level9 cp1) through the standard level
jump, players 3-4 join by Start from poll 7000 (`tests/m2/nav/m13_p3.txt`, `m13_p4.txt`). Patches (all generated with
`python -I mod/make_pnach.py`; `mod/w4p_m1.pnach` was NOT regenerated because a 4-instance batch uses it):

the [warriors-4p missions] group as it is now in `mod/m2/missions.txt`; the other groups were kept as in

### 1.2 Design and code
- Hooks: the two binding calls jump to stubs TPW/TFW (they load the core address into t9); the common wrapper X4W calls
  the core with the binding's arguments unchanged, then X4F(handle).
- X4F(handle): stop if X4_ON = 0; object (FUN_00390268) -> human (FUN_00229868) -> player index must be 0 or 1; for game
  player index 2..count-1 (at most 3): if TestDistance(X4_DIST = 15.0, his handle, player 1's handle) = 0, call the
  HuTeleportNearHuman core (his handle, player 1's handle) and count it in X4_N.
- Runs inside the Lua binding call on the game thread, the context in which the game's own HuTeleportNearHuman runs.
- No cinematic check (negative result 5). X4_ON / X4_DIST are startup-only data words (the tests write X4_ON over PINE).

## 2. X6: running Lua source in the game

### 2.1 Where the lua_State is (VERIFIED static + runtime; was BLOCKED)
- **Script object pointer: 0x00512B04.** FUN_00356390 allocates the object (tag string "ScriptLua" 0x00578F98, source
  path 0x00578FA8), calls the constructor FUN_003564D8 and stores the result at 0x00512B04 (`sw a0,0x2b04(v0)` at
  0x00356428). FUN_00356450 frees it and stores 0. ResetLevel FUN_001607B8 calls FUN_00356450 (0x00160B9C) and then
  FUN_00356390 (0x00160BAC; also 0x00160FD0): **a new script object and a new lua_State at every level (re)load.**
- **lua_State = object + 4.** The constructor (vtable 0x005449B8) stores `FUN_0032F698(1024)` (lua_open, our label) at
  +4 (`sw v0,0x4(s0)` at 0x00356528) and registers the libraries with it: FUN_00331A58, FUN_00326548 (base library with
  `dostring`), FUN_0032C628, FUN_0037D420 (the game's bindings); `_ERRORMESSAGE`/`_ALERT` are C functions
  0x00357BA8/0x00357BB0 that just return 0 (Lua errors are silent).
- **Object methods (vtable 0x005449B8):** +0x2C DoString FUN_00356A78(obj, source, name) = lua_dobuffer
  FUN_003290D0(L, source, strlen FUN_00430EB0, name); +0x34 DoFile FUN_00356AF8(obj, path); +0x3C DoBuffer
  FUN_00356AD0(obj, buffer, size, name) = lua_dobuffer(*(obj+4), ...). FUN_003290D0 has three callers: 0x0032576C
  (Lua `dostring`), 0x00356AAC (DoString), 0x00356AD8 (DoBuffer).
- Runtime (dynamic, M13 after the level jump, x4x6a-d): 0x00512B04 = 0x00C8E600, vtable 0x005449B8, L = 0x00C9DA00
  (the same in every run).
- Not it: a second `lua_open(0x40)` at 0x0040A538 (FUN_0040A510) makes a small helper state at 0x005147A0.

### 2.2 LUARUN
LUARUN(a0 = NUL-terminated Lua source, a1 = chunk name or 0 -> "=w4p") at 0x000E79A0 returns -1 if there is no script
object or no lua_State, else calls DoString 0x00356A78 and returns lua_dobuffer's status (0 ok, 3 syntax error).
Callable from the W4P call mailbox (CallAt in sessions; the source must then already be in RAM, e.g. as pnach data)
and from tests. It ran from the FrameStats mailbox point (outside any Lua call) in all tests.

### 2.3 LUACH: our Lua right after a named script file
Every script file goes through DoBuffer FUN_00356AD0 (DoFile 0x00356C18 and the preload callback FUN_00356D00 call
vtable +0x3C). LUACH replaces DoBuffer's `jal 0x003290D0` (0x00356AD8): it runs the file, logs the name (ring of 8 x 32
bytes at 0x000E7B00, counter LC_N 0x000E7AFC), then walks the table LC_TAB (0x000E7F00, rows {name pointer or 0 = every
file, source pointer}, source 0 = end) and runs each matching source with lua_dobuffer(L, source, strlen, "=w4p")
(counter LC_RUNS 0x000E7AF8). Our sources run through 0x003290D0 directly, so they never re-enter LUACH. Because the Lua
state is new at every level load, a row runs again after a reload and nothing leaks into the next mission.
- **When a fix runs:** right after the file that defines the function it changes, before the game can call it (for
  example "level9.lua" defines `EnterGraveTrain`; x4x6c/d show the wrapped function in place at the first call).
- **Where the fix text lives:** pnach data (startup-only words). Now: table 0x000E7F00-0x000E7F0F, the M13 name at
  0x000E7F40, its source at 0x000E7E00-0x000E7EB7. Room for more rows: 0x000E7F10-0x000E7F3F (6 rows) and, for more
  text, the free 0x00096000-0x0009FFFF (STATE.md; observed zero F-0050/F-0125; check first).
- 0x000E7C00-0x000E7DFF is a test-only buffer (`tests/m2/x4x6_probe.py` writes Lua text there over PINE).
